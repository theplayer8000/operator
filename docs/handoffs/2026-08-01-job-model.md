## This session's change: the profile had no UI half

`be24f09` changed the server and not the page. Every denial still rendered with
an **"Allow this"** button that writes a rule into
`.claude/settings.local.json`. For the five standing denials that button cannot
work — `--disallowedTools` is a deny, and a deny beats an allow — so it would
write a rule that sits in the settings file looking effective and is refused
every time it is used.

That is the same failure mode as the Windows path-matching bug documented at the
bottom of `jobs.mjs`, arriving from the opposite direction. That one cost three
denied grants to diagnose. It also contradicts the decision itself: the whole
point is that publishing and deleting are the owner's to run.

**Now:** a denial carries `standing: true` when it hit the profile. The card for
one hands over the command to run instead of offering a grant, and `allowRule()`
refuses to write such a rule even if an old tab asks it to.

### The matcher over-matches on purpose

The two sides are written differently — the profile holds patterns
(`Bash(git push:*)`), `describeDenial` generates the exact refused command
(`Bash(git push --dry-run)`) — so `matchesStanding()` does a bare prefix compare
with **no word boundary**. `git pushup` therefore reads as standing.

That is the direction to be wrong in. Over-matching tells the owner to run one
command himself that he could have granted. Under-matching puts the grant button
back on a refusal the deny list will keep refusing, which is the inert-rule bug
above. Claude Code's own `:*` semantics are the authority and are not documented,
so this leans toward "the profile covers it".

Verified against the real `describeDenial`:

| Command | `standing` |
|---|---|
| `git push origin main` | `true` |
| `git push --dry-run` | `true` |
| `rm -rf dist` | `true` |
| `rmdir tmp` | `true` |
| `git pushup` | `true` — the deliberate over-match |
| `npm run build` | `false` |
| `git commit -m x` | `false` |
| `Write` → `server/jobs.mjs` | `false` |

## Architectural decisions

None new. The event vocabulary is unchanged — `standing` is a field on an
existing `permission_request`, not a new event type, which keeps the contract in
`ai-workspace-design.md` intact for a second provider.

One thing worth recording for whoever does step 2: **the deny list is what
actually holds the line**, and it was measured, not assumed — `dontAsk` denies
ordinary file writes too, `bypassPermissions` denies only the list. Both checks
are written down at the `--permission-mode` flag in `jobs.mjs`. Re-run them after
any Claude Code upgrade; if a future version stops honouring `--disallowedTools`
under bypass, this becomes an unrestricted agent silently.

## Technical debt

**Resolved:** none from the register.

**Introduced:** none. Two pre-existing things surfaced and are recorded below
rather than filed, because neither is Operator's own code:

- **`server/workspace.mjs` is dead code** — 472 lines, no importer. Deleting it
  needs the owner (see the command at the end).
- **A broken `node` shim shadows the real binary.**
  `D:\projects\node_modules\.bin\node` — one directory *above* this repo — is on
  PATH ahead of `C:\Program Files\nodejs\node.exe` and points at a POSIX path
  that does not exist on Windows. It fails silently: `node --check` exits 0
  having run nothing, and `node -e` prints nothing at all. Any session verifying
  server code with `node` is verifying nothing. Use the full path.

## Recommended next milestone

**Step 3 — split the runner into its own process — before step 2.** The design
doc orders them 2 then 3, and two things have changed since it was written:

1. **Step 2's headline justification is largely spent.** It exists to fix
   limitation ② with in-turn permission answers. The standing profile fixed ②
   by removing the interruptions instead, and the two remaining denials are
   deliberately *never* answerable in-turn — the owner runs them. What step 2
   still buys is mid-turn interjection, no re-spawn per turn, and a tidier path
   for attachments. Real, but no longer the headline.
2. **Step 2 cannot currently be verified.** A rewrite of the runner is a rewrite
   of `server/jobs.mjs`, which only takes effect on restart — and a restart kills
   the job doing the work, because the runner is inside the server. That is
   limitation ④ exactly, and it means step 3 is a prerequisite for testing step 2
   from inside Operator rather than merely a later nicety.

Step 3 also has a cost the owner should agree to first: a second process to
supervise, which `ai-workspace-design.md` names under *What this costs*.

## Assumptions & risks

- **Deny-beats-allow in Claude Code is reasoned, not measured here.** It is
  standard permission precedence and the profile's own measured behaviour is
  consistent with it. It is also not load-bearing: the owner's decision alone
  makes the grant button wrong for these five.
- **`matchesStanding` is not Claude Code's matcher**, only a close reading of
  it. The over-match is the safe side; see above.
- **The standing card was not seen rendering.** Producing one means asking a job
  to `git push`, which is denied and would put a genuine refusal in the log. It
  is a pure-render branch behind a boolean and both gates are clean, but it is
  untested in a browser.
